# 支付异常闭环实施契约（2026-10-16）

状态：普通人工账单整单外部退款登记、独立复核与财务追溯已实现并通过[隔离集成验收](external-refund-acceptance-20261016.md)；可信关单及完整业务冲正尚未完成。承接 [核心替代目标](core-replacement-goal-20261016.md) 第二阶段；既有资金保护继续有效。

## 当前事实与实施顺序

[10-13 真实验收](real-payment-acceptance-20261013.md) 已证明指定 MPAY 商户的 0.01 元扫码及真实异步通知可用，不能再按旧文档称全部支付失败。标准主动查单当时返回 404；本次对同机 MPAY 源码只读核对，未发现可依赖的标准 `/api.php`、可信最终关单或退款查询契约。后台改状态、补单、删除订单、QR 倒计时和静态收款码都不能证明付款入口已经不可收款。

先实现与商户能力无关的外部退款事实记录和独立复核，再为具体渠道补可信查单/关单适配。只有源码分析不计真实商户验收通过；没有可用商户能力时保持待核验，不能添加“我已关单”复选框绕过付款限制。

## 资金事实与状态边界

- 原 `payment_transactions.status=succeeded`、原收款流水和回调幂等记录永久保留。退款追加独立出款事实，不将收款改成退款以免抹掉收入或破坏重复通知处理。
- 外部退款不得记入客户余额；不得直接复用 `RefundInvoice` 的余额退款路径。现有实现还涉及库存、任务、续费期限及升级冲正，必须按业务分支拆出明确规则。
- 退款登记保存原支付、账单、客户、金额分、渠道实例、原流水、退款流水、实际到账时间、资金路径、证据引用及摘要、申请人/复核人、版本和审计。凭证不含密钥或完整个人敏感数据。
- 区分原路退回、人工转账与其他人工退付。商户显示受理不等于实际到账；未知结果进入待核验，不能创建出款事实或反复重试。
- 第一增量只允许无资源、无订单、无信用、无升级/续费/流量/佣金关联的普通人工账单整单退款；超出范围明确拒绝并解释。此增量不等于第二阶段全部完成。

## 拟定数据与接口

迁移 143 新增独立 `external_refunds` 和 `external_refund_operations`，状态为 `pending_review / confirmed / rejected`，金额为整数分、仅匹配原单全额；支付/账单关联、幂等键与原商户退款流水有数据库唯一保护。原商户身份从支付加密快照提取 APIURL/PID，规范 scheme/host/default-port/尾斜杠并计算摘要，不包括密钥；跨支付类型和复制实例共享唯一约束。不同域名实际指向同一商户的网络别名无法自动推断，需要未来明确映射，不能宣称全网商户身份已识别。已确认记录不可覆写，修正通过新审计记录和专门流程处理。仅在隔离 PG18 应用迁移，运行库未变更。

后台提供账单级退款记录分页、提交登记、独立复核确认、驳回接口；设置独立的查看、登记、确认权限，默认不给普通角色隐式扩权。接口返回 `version`，写操作带 `expected_version` 与幂等键，统一错误结构；列表使用 `items/total/limit/offset`。具体路由见 [HTTP 验收](external-refund-http-acceptance-20261016.md)。

每次写事务内重验有效浏览器会话、当前员工状态/权限和客户数据范围，包括幂等重放；禁止申请人自审。固定资金锁顺序，申请/确认时都重验原支付、金额、账单/发票申请和关联资源条件。版本不符返回 409，同键异参返回幂等冲突。实际到账确认、账单退款状态及追加出款/审计必须原子提交，原支付成功状态保持不变；后续重复成功通知仅重放原结算结果，不重新开通或产生佣金。

驳回只结束待复核记录，不改变资金或账单；因此保留会话、权限、范围、同账单关联、版本和禁止自审校验，但不要求账单仍满足出款资格。登记后出现发票申请等阻断时，确认拒绝、驳回仍可执行，防止登记记录卡死。

驳回记录保留不可变历史；原退款流水可用新幂等键和补正证据重新登记。商户流水唯一约束仅覆盖 pending/confirmed，既有创建/驳回幂等键仍重放原结果，不覆盖旧记录。

财务展示原收入、退款支出与净额三者，并能追溯到同一原单。当前只有申请记录的退款不影响已付账单或统计；确认后才生成一次支出与业务冲正。部分退款和有交付订单必须独立设计库存/期限/佣金处理，不能默许同一路径。

## 可信关单与迟到通知

未来适配器必须声明能力，支持带商户操作号的幂等关闭及可信终态查询，明确最终不可付款的语义和回调一致性窗口。仅在确认未收款且不可再收款后，才能通过正式事务关闭旧意图并解除付款限制；外部网络调用在行锁事务外执行。

主动查单或关单与通知竞争时，在事务内重读资金事实，已成功收款必须优先；失败、超时、404、未付及本地 expired 均不解锁。释放后出现异常迟到收款必须隔离核验，禁止对新旧两个意图都重复交付；该竞争测试通过前不开放关单能力。指定 MPAY 不满足此契约，继续显示人工核对说明。

## 验收标准

1. 强制隔离 PG18：迁移、HTTP 契约、权限/客户范围、撤权/过期会话、申请人自审拒绝、409、同键重放/异参冲突、不同键并发重复退款、同一商户退款流水复用、无余额入账及失败原子回滚。
2. 原支付成功事实和收入保留、退款支出只记一次；重复原签名回调、并发确认、相关业务拒绝、发票申请竞争均有实际 DB 断言。测试模拟渠道仅用于协议与竞争，不作为真实退款证据。
3. 四尺寸浏览器验证申请、取消、审核、驳回、权限拒绝、版本冲突、重复提交、真实空态/分页和错误恢复，所有数据来自 Go API。
4. 真实商户查单/关闭/退款逐项单列：真实付款人到账与商户流水闭合才算资金验收。当前授权内先完成本地实现及隔离测试，不调用真实退款、关单或伪造补单；正式资金动作按具体商户和订单取得授权。
5. 客户/订单/续费/佣金等完整冲正、可靠关单及真实外部验收全部闭合后，才标记整个支付阶段完成。受商户能力限制的条目保持待验收，其他可实施工作继续。
