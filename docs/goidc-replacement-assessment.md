## 审计口径与证据

本报告按业务能力闭环估算，不按旧 URL、payload 或 MySQL 表逐一复刻。百分比是审查者对“成功、失败、未知、恢复、权限和外部回读”共同覆盖程度的估计，不是代码行数、路由数或测试通过率。凡依赖真实商户、真实供应商、正式公网、历史业务快照或客户收件的事项，隔离夹具不能替代生产证据。

当前覆盖扫描结果为：旧 PHP 1,352 条 Route 调用声明，新 Go 578 条注册且 578 条唯一注册，精确方法/路径候选 1 条；`covered` 189、`frontend_replaced` 40、`superseded` 52、`deprecated` 46、`missing_candidate` 1,025。该结果来自 `node scripts/route-coverage.mjs --strict`，只能作为兼容风险索引，不能直接换算业务替代率。

## 2. 停用旧 PHP 的硬性卡点

### P0：全站停用前必须关闭

1. **正式切流、回退和数据恢复没有生产证据。** 隔离双 Web、切换/切回和短时资源保留已经通过，但真实 HTTPS/安全 Cookie、维护页和支付回调、正式资源保留窗口、历史 schema 升级、授权业务快照恢复以及生产回滚尚未演练。隔离相同 schema 不能证明旧业务库可切回。
2. **支付可信关单与退款到账未闭环。** `internal/store/payments.go:242-395` 已把验签、金额、账单、重复回调和迟到收款放进事务；`internal/payment/epay_query.go:43-88` 对非 200 直接返回不可用，当前标准商户查单返回 404 时系统只能继续冻结并人工核验。`internal/store/finance.go:435-464` 明确充值退款未开放，已还信用等情形拒绝自动退款。没有真实 0.01 元支付、丢通知查单/关单、退款到账和重复对账证据，不能把“代码写了”当作资金闭环。
3. **复杂资金冲正仍非通用能力。** 普通人工账单、未消费本地续费和未交付人工新购已有事务事实；已消费服务、上游续费、已交付服务、升级/降级、佣金、信用已还款、部分退款和自动原路退款仍需人工或被拒绝。该边界必须按实际启用商品逐项签字，不能用一个 `RefundInvoice` 入口概括。
4. **若部署接管存量，迁移复核是 P0。** 当前导入主动把历史账单/服务设为待复核，禁止支付、续费和资源任务；10-09 演练保留 245 条 issue，10-14 新快照因源库新增订单/账单/服务上升为 247 条（`docs/cutover-runbook.md:224-229`）。未完成逐条复核、冻结快照、密码找回和回滚演练前，旧 PHP 仍是存量客户的事实来源。

### P1：首轮上线前必须按产品范围关闭

1. **G07/NOKVM 真实资源动作。** 魔方适配器和 NOKVM 客户端都在隔离测试中具备协议框架，但真实账户、真实母机、暂停/恢复/终止、升级和自动续费回读未验收。`internal/provision/nokvm.go:381-398` 对重装明确返回 `reinstall_confirmation_pending`；`docs/nokvm-delivery.md:81-83` 明确 VNC、流量计费和超额自动暂停未完成。
2. **Worker 容量和恢复边界。** `internal/store/services.go:647-707` 将已发送但租约过期的写任务置为 `waiting_verification`，这是正确的保守保护，却会把外部事实交给人工核验；目前没有目标容量、完整故障点、RTO/RPO 和正式角色/状态矩阵证据。
3. **后台高影响操作页仍是部分实现。** 只读页面不能替代资金审批、供应商运维、资源管理和订单创建。优先项见下一节。
4. **通知和客户协同。** SMTP/SMS/outbox 有实现和隔离测试，但真实收件、死信/人工重试、客户站内收件箱、工单上游同步和高级字段仍未验收。缺通知不会总是阻断空库上线，但会阻断以旧站作为完整客户服务替代。

## 4. 下一阶段路线图

1. **先决定部署边界。** 明确是空库新站还是接管旧客户；若接管，先冻结旧 MySQL 快照、逐条处理当前快照的 247 条 issue（历史 245 条基线需保留差异说明）、完成金额/资源/密码复核和可恢复回滚点。
2. **完成真实支付专项。** 选定测试商户，验证 0.01 元下单、异步通知、通知丢失后的查单/关单、重复回调、原路退款到账和对账；对充值、上游续费和已交付服务分别出拒绝或闭环矩阵。
3. **完成真实供应商/NOKVM 专项。** 按实际售卖商品逐动作测试成功、超时、强杀、未知回执、人工核验、回读和回滚；明确哪些动作保持关闭，避免把 unsupported 当成功。
4. **收口订单、流量和供应商后台。** 先核实 #8/#99、#10/#70、#90/#94、#91/#93，再补批准范围内的商品升级和第三方身份；独立人工库存须先冻结口径；每组同时验 API、权限、冲突、未知结果和移动端。
5. **建立 Worker 生产门槛。** 用冻结的目标负载完成稳态/峰值/恢复测试，记录 p95/p99、错误率、积压排空、RTO/RPO 和人工核验时限；把 `waiting_verification` 的责任人、SLA 和重复操作规则写进运行手册。
6. **最后做切流演练。** 在保留旧 PHP 可回退的窗口内演练公网 HTTPS、维护/回调、Cookie/会话、数据库备份恢复、灰度、切回和资源清理；验收材料齐全后再讨论停旧 PHP。
