# Supplier Task Queues (Pages 90 and 94)

`/admin/suppliers/jobs` (legacy `#/commodity-taskQueue`) and `/admin/suppliers/tasks` (legacy `#/task-queue`) are two permissioned views of the same persisted supplier `provision_jobs` rows. They share a component and query contract; neither invents a separate queue. The first uses `products.view` and exposes safe retry to users who also have `services.manage`. The second uses `jobs.view` and emphasizes task inspection; it shows the same retry action only to authorized service managers. These pages do not include email, SMS, manual, or NOKVM tasks.

`GET /admin/supplier-jobs` and `GET /admin/supplier-tasks` accept `customer_id`, `supplier_id`, `action`, `status`, `q`, `from`, `to`, `limit`, and `offset`. Filters and pagination persist in the URL. Rows are scoped with `admin_customer_allowed` and belong to the supplier identified by the service's immutable `delivery_snapshot`, not the product's current binding. Returned columns are limited to names, IDs, action, status, timestamps, attempt count, and safe action flags. `result`, `request_payload`, credentials, and raw `last_error` are never selected.

`POST /admin/supplier-jobs/{id}/retry` requires an `Idempotency-Key` and JSON `expected_attempts` plus `expected_updated_at`. It only re-arms a failed `sync` job whose `external_started_at` is null, service is active or suspended with an upstream ID, and service has no other inflight job. It checks the exact attempt count and update timestamp, active session and service-management grant, customer scope, reviewed service, and supplier-account lease under transaction locks. The original job ID and upstream idempotency key remain unchanged. The operation receipt makes an identical request/key replay return 200 without scheduling again; a different payload with the same key returns 409. The page stores an uncertain request's exact body, key, and URL in per-admin session storage until a definitive response arrives. A pending worker may later perform the external call; the HTTP request itself does not contact the supplier. `waiting_verification` and failed jobs with an external start timestamp require operator reconciliation in the service detail page and cannot use this retry endpoint.

The legacy pages displayed Customer, Product, Action, Description, Source, Status, Last Operation Time, and Operation. The new table preserves these eight columns. The supplier name is shown in Source, and the action uses the persisted provision action. Failed rows expose retry only when the server can prove they were not dispatched; unknown outcomes show a verification link. Loading, empty, error, refresh, and pagination states are handled by the shared page.
