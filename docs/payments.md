# 在线支付

Go API 原生实现易支付标准 MD5 协议，支持支付宝、微信、QQ 钱包和网银渠道。旧 PHP 插件仅用于核对协议；没有读取旧商户密钥或依赖 PHP。Next.js 负责选渠道、创建支付单和跳转网关，Go 只提供 API。模拟支付默认关闭，未配置商户时不列出在线渠道。

## 配置与接口

部署环境配置 `EPAY_API_URL`（网关根地址）、`EPAY_PID`（数字商户号）、`EPAY_KEY`（商户密钥）和 `EPAY_TYPES`（逗号分隔 `alipay,wxpay,qqpay,bank`，配置商户后默认 `alipay`）。部分配置、重复或未知渠道会令启动失败。密钥至少8字符，不返回给浏览器，不从旧库自动提取。

`PUBLIC_ORIGIN` 是客户站点来源，必须让商户服务器访问到回调。网关和站点地址使用 HTTPS；仅 loopback 地址允许 HTTP，供本地开发及协议夹具使用。配置真实商户时应使用公网 HTTPS 站点，重启 API/worker 后再检查渠道目录。网关请求使用 `<EPAY_API_URL>/submit.php`；不支持需要额外接口、RSA 或新版 JSON 协议的网关。

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/payment-providers` | 已登录客户读取已启用渠道名称、标签及模拟标记，不含配置或密钥 |
| `POST /api/v1/invoices/{id}/payments` | 本人账单创建付款意图；提交 `provider`、`expected_version` 和 `Idempotency-Key` |
| `GET/POST /api/v1/payments/epay_{type}/webhook` | 商户异步通知，GET 查询参数或 POST form，提交成功后返回纯文本 `success` |
| `GET /api/v1/invoices/{id}` | 本人读取待处理支付的跳转链接，刷新后可继续原付款 |
| `POST /api/v1/invoices/{id}/payments/{payment_id}/reconcile` | 本人主动查询待处理在线支付，确认已付款后补结算 |
| `POST /api/v1/admin/invoices/{id}/payments/{payment_id}/reconcile` | 有 `payments.reconcile` 权限且在客户范围内的管理员主动查询 |

客户账单详情点击“在线支付”，选渠道后创建支付单，再点击“前往付款”。付款链接打开新标签页；浏览器返回客户账单页面只触发读取，不标记已支付。后台账单详情隐藏可付款链接。现有 `mock` 的 POST JSON、HMAC-SHA256 和 `X-Payment-Signature` 协议保留。

## 金额、通知与并发

签名按旧插件规则排序参数，排除 `sign/sign_type` 和空值，将解码后的 `key=value` 用 `&` 连接并追加密钥，生成 MD5。所有金额以整数分处理，输出两位小数；通知拒绝浮点指数、NaN、三位小数、重复参数、错误商户/渠道、无效支付引用和非成功状态。

独立随机商户付款号关联账单；schema060 添加流水字段和跨易支付渠道唯一索引。schema087 起新单保存网关地址及 PID 摘要与 `trade_no`，不同网关可使用相同商户号和流水号；历史单继续使用 `PID:trade_no`。回调在事务中校验付款号、账单、金额、状态及流水，再结算账单和写审计。订单付款进入交付队列、升级付款进入升级队列，已启用服务的续费直接延长到期时间；人工账单不产生服务任务，不扣客户余额。

同一账单只能有一个待处理付款意图。在线意图存在时，换渠道、余额支付、取消订单或升级都拒绝；人工账单已有的编辑/作废/合并限制继续生效。页面禁用余额支付并提示继续原支付单。**本地 `expires_at` 只描述本地有效期，不能证明网关已关单，因此不会释放以上限制。** 并发取消与付款遵循相同的账单锁顺序；重复通知不会重复结算、延期或创建任务。维护模式继续接收签名通知。

仅事务提交成功后回复 `success`；业务冲突回复 HTTP409 `fail`，数据库/审计等内部错误记录服务日志并回复 HTTP500 `fail`，供网关重试。未知或未启用渠道拒绝，签名错误 HTTP401。已支付外部账单禁止退款至余额，防止假退款。

## 主动查单与补结算

schema061 增加 `payment_reconciliation_checks`，记录操作人、开始/结束时间、查询状态及固定内部结果码，不保存网关原始错误文字或商户凭据。客户与有 `payments.reconcile` 权限的管理员在账单付款记录中点击“查询付款结果”；管理员还须拥有对应读取权限，现有角色不会自动获得新权限。

API 先验证本人归属或管理员客户范围、启用状态和能力，事务预约查询后释放数据库锁，再向配置的网关发起 `GET /api.php?act=order&pid=...&key=...&out_trade_no=...`。这是易支付 V1 按商户订单号查单；旧 PHP SDK 的 `queryOrder` 仅按网关流水号查询，该形状不会被宣称支持所有旧网关。网关需支持 `out_trade_no` 查询，不支持或返回未知/缺失字段时保留原支付单。

传输使用默认 HTTPS 证书校验、10秒超时、64KiB响应限制，禁止跟随重定向，不继承依赖下载代理环境。错误经过归一化，不把带密钥的请求 URL、响应正文或网络错误对象记录到日志/返回给客户。JSON 拒绝重复键和尾随内容，精确验证 `code=1`、商户、类型、商户订单号、网关流水号及整数分金额；仅 `status=1` 为已付款，`status=0` 表示仍待处理，其余值不能放行。

预约按支付单串行，同一支付单30秒内拒绝重复查询；1分钟预约期限允许进程崩溃后重新发起查询。查询期限只保护查询任务，不会关闭付款单。已付款结果与付款事件、账单结算、查询完成记录及审计原子提交，使用独立 `query:<商户流水标识>` 事件身份，后续真实通知可安全重复到达。提交前重新检查客户范围、账户和管理员权限，等待网关期间撤权/停用/客户转交不会产生补结算。查询返回待处理但回调已先提交时，以本地已付款状态为准，并校验真实流水一致；不会回退为未付款。查询失败、金额不符、未付款或查询期限失效均不会解除原付款限制。

验证覆盖精确金额/重复字段、商户/类型/订单关联、拒绝重定向与不可信证书、超时信息脱敏；PG18 覆盖查询冷却与并发预约、查单/回调竞争、迟到通知、审计回滚、客户转交/撤权/停用再校验及崩溃预约恢复。浏览器验证了本地网关确认但不发送通知时账单仍未付款，客户主动查询后补结算并显示查询历史；手机付款记录在自己的表格区域滚动，页面无横向溢出。真实网关退款和关单协议未有充分契约，当前不以查到“未付款”代替关单。

查询协议补充参考：[易支付 V1 SDK](https://github.com/nb-sb/epay-sdk/blob/main/epay-sdk/src/main/java/com/nbsb/epaysdk/protocol/epayv1/EpayV1Adapter.java)。本地核对副本与测试证据保留在 `output/reconciliation-20261006/`；此参考及本地模拟验收不能证明真实商户兼容性。

## 自动对账

schema067 为支付单增加 `next_reconcile_at` 和 `auto_reconcile_attempts`，查询历史增加 `source=manual/worker`。手动查询必须有操作人，worker 查询操作人为空；系统审计明确记录来源。账单读取权限足以查看查询来源、最近结果、下次计划时间和用完次数状态；主动查询仍需要原有归属或 `payments.reconcile` 权限。schema087 起已有快照的支付单使用原商户查询，即使当前渠道停用或配置移除也继续核验。

## 本地过期与商户轮换

schema087 为新易支付意图保存不可变、绑定付款号的 AES-GCM 凭据快照，必须设置 `PROVISION_ENCRYPTION_KEY`。后台商户轮换仅被有效期内的 pending 支付单和活动查单租约阻止；历史无快照单先使用原配置加密补齐。未结算单原凭据已经遗失时拒绝轮换；成功/失败终态旧单写入加密“不可用”标记，允许新商户配置但不误用新凭据。

worker 每轮将超时易支付单标记 `expired` 并重置查单计划，随即尝试查询，后续保留有限重试和退避。`status=0`、未知结果或网络失败均不表示上游关闭。过期后解除的是商户配置锁定，账单继续保持付款限制；原商户迟到回调或后续查到已付仍能一次结算。没有实现可信关单接口。

schema086 将模拟支付默认值改为 false，未主动保存配置时使用 `PAYMENT_MOCK_ENABLED`（默认 false）。主动保存的后台配置保持不变，升级不能代替检查已开启的模拟通道。

配置商户后 `cmd/worker` 自动启动独立支付循环，每10秒最多处理一单，不占用开通/邮件工作循环。支付意图创建2分钟后首次查询；第1–3次后等待5分钟，第4–6次后15分钟，第7–12次后1小时，第13–31次后6小时，最多32次。所有已发送查询、错误或进程退出后的租约都计入上限。达到上限停止自动查询并提示人工核对，不改变支付状态；显式手动查询重新开启2分钟后的自动跟进。查到已付款或收到成功回调时清除计划。

预约使用支付行锁及 `SKIP LOCKED`，多个 worker 和手动查询共享每单唯一活动查询及30秒冷却。查询在数据库事务外执行；完成必须匹配持久化查询身份、渠道、归属、金额与未失效租约。1分钟后失效的查询可被恢复，旧进程结果不能结算。自动成功复用签名回调的结算事务，状态、付款事件、查询完成和审计一起提交；回调先成功时待处理查询只记录已付款，不回退状态。异常结果、超时或落库失败保存固定错误码，并依退避继续查询。进程退出使用独立短上下文记录错误后再关闭连接池。

自动查询属于系统收款结算，和成功回调一样会处理账户已停用或维护期间的有效既有付款；它不使用某个管理员的身份或销售范围。手动查询的撤权/停用/转交再检查规则继续生效。**自动查询未付款、订单不存在或本地付款期已过都不代表关单，不解除在线付款限制；迟到成功通知仍可结算。**

旧 SDK 的退款请求为 `POST /api.php?act=refund`，表单携带 `pid/key/trade_no/money`，但未提供商户退款号、幂等保证或退款结果查询。参考 SDK 的退款成功码只确认受理，且参考与 MPAY 方言分别使用0和1。当前没有足够契约证明退款资金已回到原渠道，也没有可靠关单接口，因此不发送该退款请求或伪造完成记录；后续接入需明确方言、持久化请求、未知结果核验与实际资金确认。
