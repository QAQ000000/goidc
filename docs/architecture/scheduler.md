# 内部调度任务契约

状态：当前生效。任务目录位于 `internal/scheduler`，Store 绑定业务入口，worker 保持原有执行循环；后台日志 API 与页面使用同一份编译目录。

## 任务与执行边界

| 任务键 | 名称 | 调度位置 | 启动时运行 |
| --- | --- | --- | --- |
| `automatic_payment_reconciliation` | 自动支付查单 | 独立循环，每 10 秒轮询 | 否 |
| `affiliate_settlement` | 推介佣金结算 | 分钟循环第 1 项 | 否 |
| `service_expiry_notifications` | 服务到期通知调度 | 分钟循环第 2 项 | 否 |
| `billing_notifications` | 账单通知调度 | 分钟循环第 3 项 | 否 |
| `overdue_service_suspensions` | 逾期暂停入队 | 分钟循环第 4 项 | 否 |
| `automatic_renewals` | 自动续费处理 | 独立循环，完成后等待分钟 ticker | 是 |
| `supplier_sync_schedule` | 供应商同步调度 | 原 2 秒交付循环内，恢复过期租约成功后 | 否 |

频率是 worker 轮询节奏，不保证完成时限。分钟循环四项串行执行，单项出错后继续下一项；支付、自动续费、通知调度分别运行。供应商调度仍位于原领取交付任务之前，恢复失败时跳过本轮。ticker 的积压与慢任务行为沿用 Go 原有逻辑，不增加补跑。

目录只管理这 7 类已有调度审计的业务入口。通知投递、邮件/短信 outbox、实名认证处理、文件回收和启动恢复保留各自生命周期。此目录不是前台应用渠道，不进入适配器模块清单；也不提供上传脚本、动态 cron、手动执行或自动重试接口。

`service_expiry_notifications` 在原分钟循环内补扫精确期限后 72 小时以内的 `service.expired`，不补跑过去的调度轮次。阶段固定为 0，服务与精确期限形成稳定去重身份；重启和并发不重建已有事件。跨上海日界的补偿只向期限前已具备路由、模板及用户渠道资格的收件人投递，事后启用或订阅记为跳过。提前提醒只取当前上海阶段，账单催缴仍按当前未付事实逐日运行；旧邮件、短信的候选、去重日期、模板日期和发送前校验统一上海日界。完整规则见[通知契约](../notification-architecture.md#业务事件与订阅范围)。

## 审计、取消与未知结果

- 普通 6 项通过已有 `RunScheduled` 写开始及结束审计。开始或结束审计写入失败都不重跑业务；结束未确认可以保留 `running`，不能凭此重发。
- 自动续费直接进入 `RunDailyAutoRenewals`，保留数据库日边界、跨 worker 事务 advisory lock、固定候选上界、游标和已支付账单幂等。只有日全量完成才写成功的 `is_full_pass`，外层 runner 不再包装一次审计。
- 自动建单在同一事务记录不可变的账单、服务、客户、原到期日和代次来源；付款在原余额事务内再次核验来源、开关、期限、代次和取消状态。客户自选的幂等键不能授权自动扣款。余额不足或进程中断留下的未付账单保留供人工处理，后续调度和充值不会自动追扣。
- 供应商报价返回的实际到期日超过数据库当前时间 24 小时窗口时，自动路径只向前同步本地期限、清理旧错误并记录 `supplier.auto_renewal.skipped`，不建单、不扣款、不计作成功续费。手动提前续费仍允许，细节见[供应商协议](../supplier-protocol.md#automatic-renewal-admission-and-payment)。
- `overdue_service_suspensions` 先处理既有逾期账单，再在剩余额度内扫描无未付账单但已到期 24 小时的 Active 供应商周期服务，最后处理既有付清恢复；不新增调度键或循环。到期扫描排除导入复核、批准取消和未决任务，只创建固定期限来源的暂停任务，不建单、不扣款、不提前改状态或发通知。自动派发要求 Suspend＋Sync 并 fresh 核对上游原资源、商品和期限；远端期限更晚、尚有权益或非 Active 只同步观察并取消未派发任务，更晚但仍过期的期限留下一轮按新来源扫描；Active 远端期限更早则保留本地权益并转人工待办。协议同秒视作同一期限，微秒来源不变；读取失败不发送写操作，能力缺失进入人工待办。规则见[供应商生命周期](../supplier-protocol.md#billing-suspension-and-paid-recovery)。
- runner 对未知任务键和已取消的上下文拒绝执行；业务回调接收原 worker 上下文。各业务已有的单次超时、批次大小、事务、租约及退款/付款围栏继续由业务实现负责。
- 不添加统一超时、错误重试、并行化、panic 恢复或跨进程互斥。外部写结果未知继续使用原业务的核验流程。
- 任务失败的后台记录只显示安全错误码，不保存远端响应或凭据；运行日志仍遵循各业务已有的脱敏规则。

## 日志 API 与前端

超级管理员的 `GET /api/v1/admin/logs/jobs` 保留分页、日期、状态和任务筛选，响应额外提供 `tasks` 编译目录；`task` 参数根据同一目录验证。权限与趋势接口保持原契约。

页面从响应目录生成任务筛选及显示名称，未知历史键回退显示原键；不再维护另一份名称表。日志和趋势分别加载、失败和重试。目录只描述可执行任务，不代表已启用、外部健康或执行成功。通知调度成功表示入队完成，供应商同步调度成功也不表示外部操作完成。

## 扩展与验证

新增内部任务时，在 scheduler 目录同时定义稳定键、名称、执行绑定和所属循环；在 Store 提供业务适配。同时检查 `scheduler_runs` 的任务键数据库约束，新增键须通过显式迁移扩展。复用现有循环前明确是否串行、启动是否立即执行及取消边界。新循环或新审计口径须另行评审，不能仅添加标签便宣称接入完成。

```bash
node scripts/test-scheduler.mjs --unit
node scripts/test-scheduler.mjs --integration
node --test scripts/scheduler-components.test.mjs
```

集成入口要求显式回环 PG18 `_test` 库，逐项要求 run/pass 且零 skip，覆盖真实 runner 分发、完整目录和权限、审计故障不重跑、取消、日全量去重，以及现有通知、暂停、支付查单与供应商周期同步。数据库用例串行；取消和顺序的单元夹具不替代真实 worker 进程验收。严格集成另启用既有双 worker 自动续费测试，验证启动、实际分钟 tick、重启、未知续费冻结及 TERM 退出；供应商为本地协议模拟。组件夹具不代表浏览器，真实外部渠道与生产运行分别验证。

通知补偿与旧提醒来源迁移的专项回归归现有通知严格 runner，需覆盖 UTC 会话、跨上海日界、72 小时窗口、已生成事件、并发限量排空、补偿资格和续费后失效；不能用本文件既有调度通过结果替代新增行为证据。迁移 173 须停旧 writer 后与 API/worker 成套发布，期限来源不明的旧待发提醒不回填，细节见[通知发布边界](../notification-architecture.md#后续扩展与验证边界)。

本轮自有 UTC PG18 的调度 7 项单元及 41 项集成严格 race 通过，零跳过；通知专项结果与同源候选升级验证见[通知当前验收](../notification-architecture.md#当前验收状态)和 `output/notification-catchup/summary.json`。本轮未新增浏览器、真实渠道或生产运行验收。

自动续费来源使用迁移 171，API/worker 须成套发布；升级不按历史幂等键推断来源。先停旧 writer、备份并迁移，再启用配套候选；旧自动 writer 不记录来源也不执行付款围栏，禁止混跑。回退代码不会删除已有任务历史；生产回退仍遵循[发布与切换](../migration/README.md)的构建、配置及健康检查要求。

无账单到期分支使用迁移 172 的不可变任务来源，遵循同样的停旧 writer 与成套发布边界，不回填历史暂停。该分支的 `TestSupplierExpiry*` 回归归供应商严格 runner，不能用旧调度通过结果代替新增分支的证据；真实暂停与生产运行继续独立验证。
