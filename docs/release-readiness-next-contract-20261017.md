## 4. Web 构建和回滚的明确约束

**后续防护增量：** `3dd0196` 已新增Linux `prebuild` 运行目录检查，真实同cwd的Next进程会使构建拒绝；主目录只执行检查，确实退出1。README现已要求独立目录构建。下段关于缺少该检查/说明的描述仅是本契约建立时的基线；独立发布、原子切换及旧chunk保留等缺口仍未关闭。防护及其cwd/时序/直接调用限制见[恢复记录](live-web-build-recovery-20261017.md)。

现有 `web/package.json` 的 `build` 是 `next build`，默认输出当前目录 `.next`；`start` / systemd 从固定工作目录读取同一 `.next`。README 没有阻止执行人在常驻目录直接 build，也没有原子发布/资源保留脚本或发布清单。**当前检查未覆盖常驻 Next 使用中 `.next` 被构建覆盖的风险**。只完成临时目录构建是合适的隔离验证，但不等于该风险已在正式发布流程解决或演练通过。

下一批采用独立发布目录或独立 `distDir` 构建，不覆盖运行目录；构建时的 `API_INTERNAL_URL` 会进入 rewrites 产物，应按正式目标构建并核对 `routes-manifest.json`，不能把临时API地址的构建直接晋升正式包。共享依赖软链接只适用于依赖锁定且发布期间不可变的受控准备；不能在旧进程使用的共享 `node_modules` 上执行会改依赖的 `npm ci`。

发布候选在独立端口预热后，再以已经演练的方式切换进程/代理；保留旧发布完整静态资源，验证切换前已打开页面引用的旧 chunk，避免仅保留旧目录却让请求全部落到新目录仍404。明确旧进程排空、缓存写目录权限、磁盘空间和旧发布保留期。保存 Web 全套构建及启动配置，不只保存 BUILD_ID 或 Go二进制；回滚时三服务与schema兼容性成套核对。

数据库 `Store.Migrate` 已使用单事务、事务advisory锁、SQL checksum；API/worker启动时 `CheckSchema` 校验自身要求的迁移。这些是现有保护，不等于自动down迁移或旧应用与新schema兼容。`CheckSchema` 不拒绝比旧二进制更多的迁移；因此旧进程启动成功也不能证明安全降级。必须单列“切回旧二进制且保留新schema是否兼容”和“恢复快照到独立目标”两种策略，禁止覆盖当前业务库来试错。
