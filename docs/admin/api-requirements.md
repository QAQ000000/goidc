# 后台 API 需求取舍

本文维护后台全域的需求范围和实施顺序；[API 契约](api.md)说明共同协议，[客户管理 API](customer-api.md)、[商品管理 API](catalog-api.md)与[服务管理 API](service-management-api.md)说明批准核心动作的字段、权限、版本和恢复方式。受控声明源是 [`audit/admin-api-requirements.json`](../../audit/admin-api-requirements.json)。声明不是运行证据，也不是把旧系统接口逐个复制到 Go 的任务表。

## 判定方法

逐领域核对旧规范章节、旧路由/控制器、当前注册路由和当前页面消费者，再区分业务缺口、接口缺口、前端接线与验证缺口。声明记录代表性的旧路由、handler 和源码行，以及现有 API 入口；完整当前/旧路由和页面消费候选由脚本生成，不在活动文档重复展开。

声明中的 `required` 表示当前批准范围内是否必需；`disposition` 独立表示复用、优化、新增、排除、待决策。另分别维护 API、UI 和验证状态：有 API 不等于页面接入，页面显示不等于权限/并发/外部链路验收通过。

当前声明按 **30 个领域、56 个需求组**组织，其中 **39 组为当前必要范围**。它们是功能范围分组，不是 56 个已逐动作验证的操作。扫描发现的 **105 个实际后台页面**均归属需求组；旧台账同样有 105 条，但其中含共享页面和 query 子视图，两者不能按数量视为一一对应。旧 `/admin/logs/system` 可由当前 `/admin/logs/[kind]` 提供，不能因为缺少同名目录判定 API 缺失。

| 需求处置 | 功能组数 | 实施含义 |
| --- | ---: | --- |
| 复用 | 20 | 使用既有领域接口，按页面动作核对接线与证据 |
| 优化 | 14 | 改进查询、上下文、并发恢复或验收，具体剩余工作见下表 |
| 新增 | 5 | 原四组已实现；服务人工管理分单服务、批量及价格期限批次，整组partial、UI待接 |
| 暂缓/待决策 | 7 | 包含用户明确暂缓的旧扩展及口径未冻结项目，不允许前端自行补写 |
| 排除 | 10 | 维持已确认的产品与安全边界 |

上述处置分类不等于完成状态；例如“优化”可能是后端已具备、前端未接线，也可能仍需进一步核实具体动作。当前批准的39组必要API中，原38组为 `implemented`，包含客户核心 `customers.core` 与商品核心 `catalog.core`；`services.legacy-manual-management` 为 `partial`，单服务代续费与第二批批量代续费分别维护实现和验收，第三批人工价格/期限已形成独立协议与实现，专项证据另记；第四批受限本地状态纠错已实现，可信人工收款及转移尚未实现。这些状态仅描述各组对应实现范围，不代表所有旧功能恢复或运行验收通过，也不代表 UI 已完成；客户详情、排名、库存等仍分别接线和验收。

生成器的页面依赖是**文件级候选可达**：递归本地 import、reexport、字面量 dynamic import，提取 `api`、`useResource`、`upload` 和 `download`。共享组件文件里的其他 export、客户端逻辑或未渲染分支也可能被关联到页面，不能把候选请求当成该页确定执行的操作。变量路径、动态方法和无法解析的依赖保留表达式与未知状态；动态路径命中的是候选，不会自动标为已覆盖。

表中 API 为代表入口，路径省略 `/api/v1`；完整注册、权限与源码位置以生成 inventory 为准。页面接入、API 实现和运行证据继续独立判断。

| 销售 | 设置、预计佣金、历史确认结算 | 人员/期间/条件和历史明细核对 | 预计与确认不相加，不称为已发放；正式确认沿用现有范围 |

| 站点与主题 | 站点设置、公开主题、自定义字段 | 对照当前代码消除旧配置差距说明 | 不恢复运行时任意写配置 |

| 迁移 | runs/reviews、映射、冻结和回退 | 来源、冲突及旧业务对账逐项验收 | 外部库可读和静态路由不等于真实切换通过 |

上述各领域的旧规范章节和代表旧路由证据都登记在声明源的 `legacy` 中。旧控制器路由归属只用于定位旧行为，不自动认定新旧接口语义相同；例如旧 `user_manage` 同时包含客户列表、分组与资源操作，必须继续按具体业务动作核实。

## 本轮落地与下一批边界

### 已落地的代码与盘点

- 真实注册路由采集：Go AST 扫描生产 HTTP 注册源码，保留包装器、handler、权限来源及行号；旧版路由保留 `ANY/RULE`、动态目标及未解析 include，不猜测展开。
- 后台消费者采集：发现实际页面，递归源码依赖，识别导入别名、reexport、namespace、字面量动态导入、模板路径和方法备选，未知情况显式保留。
- 需求声明：30 个领域及 56 个功能组分别记录当前代表 API、旧规范/路由来源、复用/优化/新增/排除/暂缓、UI/API/验证轴；当前必要范围39组（38组implemented、服务人工管理1组partial）。新增稳定证据路径和声明端点均与当前仓库校验。
- 客户真实摘要 `GET /api/v1/admin/customers/{id}/summary` 已实现；各 section 根据调用者权限及客户范围返回真实数据或明确的不可用状态。精确协议与测试入口见 [API 契约](api.md)。**客户详情 UI 尚未接入**，新增 API 不能消除当前页面假零值。
- 信用消费与还款已纳入现有交易事件分页和汇总；信用消费属于非现金，信用还款按 `received_at` 计真实到账，并排除同账单的 fallback 重复记录。新来源和现金字段的 UI 展示待接。
- 通知/审计日志已增加精确 `customer_id`；统一通知新增 `GET /admin/notification-deliveries/page`，覆盖目录11类业务事件的 email/sms/inbox/Telegram/Web Push，支持客户、事件、渠道、投影状态、上海期间及分页。工单/营销仍走独立日志；无法证明归属的旧消息不猜测匹配。管理员自动续费设置新增专属 `PATCH /admin/services/{id}/auto-renew`。这些 UI 均待接，不通过普通客户身份完成后台管理。
- 关联列表及订单/账单/工单创建客户选项已统一精确 `customer_id`，非法不回退全局，范围外404，最终数据查询保留范围约束；包括续费/供应商读取。资源服务视图增加精确客户/商品筛选及商品名称/到期时间；商品分组新增分页并保留数组兼容，配置备注仅管理端读写。涉及的HTTP持久化移入Store，架构豁免仅删除，不重建基线。
- 工单带key附件上传新增持久业务意图、原子成功回执及授权结果查询；已有意图未确认禁止再次Put，底层存储journal继续围栏。原UI尚未接入新上传恢复协议，无key兼容不等于幂等；不能把这项API完成写成附件交互已闭环。详细字段、错误和前端接线要求见[API契约](api.md)。
- 客户分组成员写入增加独立版本和统一回执，漏传不再清空；销售归属在锁等待后复核真实超级管理员会话，新增可选key恢复且保留旧CAS。推广三个分页增加精确客户及归因角色，客户活动增加分页并保留旧数组；对端身份/账单按范围遮蔽。列表中原有分组、销售及资料表单同步新协议，资源池复用同一销售归属组件及原请求草稿；客户详情整体和浏览器验收仍单独推进。
- 信用、合同整体退役，核心及扩展4个需求组均required=false、excluded，旧查询和回执恢复不保留；迁移184仅关闭开关、不物理清库。通用财务投影继续兼容已登记事实，不能借此恢复业务入口。
- 商品/人员排名新增严格月份/Top N JSON查询，复用折后分摊、实际业务收款和当前销售归属；total为全部候选数，UI仍未接。四类定价配置入口新增统一锁序与自然过期复核，边界见[分组定价](../domain/customer-group-pricing.md#配置写入的授权与锁序)。
- 人工钱包充值新增只读结果查询 `/admin/customers/{id}/balance-operation`，沿用客户/key账本事实，未确认不等于允许换key；充值重放核对金额与规范化备注，资金/设置锁等待后复核当前权限、范围和真实凭据。API与页面接线、数据库和浏览器证据仍分别记录。
- 客户核心按旧44条路由归并34组动作核对，补六类高级筛选、管理员未付充值账单、仅后续新建账单的推荐人修正，以及资料/联系人/字段的原凭据与提交前复核。商品核心按旧十页签23动作核对，目录事务统一首尾凭据复核，创建/复制可选稳定键回执；无键兼容与其余 CAS 接口不承诺未知结果自动重放。这两组 API 状态为已实现；独立数据库门禁另记，不把源码完成写成运行验收通过。

### 优先接线和闭环

| 顺序 | 任务 | 当前边界与完成判据 |
| --- | --- | --- |
| 1 | 客户摘要真实展示 | 接入 summary；认证、邮箱、末次登录、推荐人、服务组、工单/财务/到期指标均有真实来源。无权 section 明示无权限，空事实与不可用分开 |
| 2 | 客户修改、筛选与充值恢复 | 按[客户管理 API](customer-api.md)接高级筛选、资料/联系人版本和未付充值代建；直接钱包充值仍使用结果查询，同一意图保持原body/key，未确认继续核验，不从新key推断重试安全 |
| 3 | 客户上下文关联与创建 | 后端精确筛选与预选客户已补齐；UI接入时固定客户与返回路径，分组/销售归属已补并发及稳定重放，重置密码复用现有API，不以姓名检索代替归属 |
| 4 | 客户通知与活动历史 | 后端精确 `customer_id` 已落实，UI 接入分页及既有筛选；审计管理员 actor 和客户 subject 分开；不得返回秘密或原始外部响应 |
| 5 | 服务设置与交易事实 UI | 接入管理员自动续费专属API；呈现钱包、现金及历史消费/还款的明确来源，不恢复信用专属页、还款或付款入口 |
| 6 | 排名与库存接线及其余业务决策 | 排名API接入控制台；独立人工库存接入资源管理及既有人工交付，遵循[库存契约](../domain/manual-resources.md)；旧服务后续能力按[已批准服务契约](service-management-api.md)分批实现；自动流量交付仍待冻结口径。信用及合同不再作为待办 |

附件UI接线另需：首次上传前保存稳定key和文件意图；断网或未知结果先调用结果查询，工单/回复成功与附件未确认分开展示，不生成新key绕过未确认围栏。资源/分组新筛选及配置备注也只完成本批API与测试，现有页面未自动接入。

当前 [客户详情组件](../../web/src/components/admin-customer-detail.tsx) 仍有认证/邮箱固定状态、工单/财务占位计数、硬编码服务分组、缺少固定客户的跳转以及禁用的分组/销售入口。这些属于明确的前端工作，不能因为后端有列表或汇总接口就标记完成。

分组及优惠码规则配置使用 RBAC→管理员/角色→定价写锁→原实际凭据的顺序，目录 writer 由 `CatalogTx` 在进入目录锁前锁定主体，等待后及提交前复核原凭据。供应商导入、目录创建、商品升级与配置升级仍保留的创建权限 helper 均位于这一目录事务内，不能继续按旧调用数量推断它们绕过新边界；具体兼容、锁序和回执保证见[商品管理 API](catalog-api.md)及[分组定价](../domain/customer-group-pricing.md#配置写入的授权与锁序)。源代码边界和真实并发回归分别验证，不扩大到未审查 writer。

推荐人关系只改变后续新建账单，迁移187冻结旧账单归因并优先已有资金事实，冲突阻断升级。发布必须停止旧 API、worker、导入等 writer 后成套升级数据库及配套程序，不能混跑旧版；不改旧账单、佣金、提现或退款归属。独立客户跟进和旧头像/职业/签名/额外地域字段分别列为 `customers.crm-followup`、`customers.legacy-profile-extras` 暂缓项，不伪装为当前核心已恢复。

## 明确不恢复

1. 报表和通用数据导出；工单附件、发票等活动业务文件下载保留，合同下载随模块退役。
2. 客户退款/停用申请状态机；客户走工单，管理员经原账单或服务处置。
3. 管理员普通购物身份、URL 传会话/密钥；只允许显式、受控、可审计的代登录。
4. 客户与财务历史物理删除；运行时插件上传安装。
5. 忽略未知外部结果的通用重试；无可信渠道能力时自动退款/关单及假成功按钮。

6. 信用额度与合同全部核心及扩展，包括信用独立历史查询/还款/原付款key恢复、合同查询/模板/设置/下载。

这些是范围决策，不能在旧版差距数量中反复统计为待补 API。

旧服务 `ClientsServices::postInfo/postTransfer/hostRenew/postBatchRenew` 对应的 `services.legacy-manual-management` 已批准恢复，`required=true`、`disposition=add`、API状态partial。单服务报价、代建未付单、客户余额付款和第二批批量协议见[服务管理 API](service-management-api.md)；第三批人工价格/期限独立实现及验收，第四批受限本地状态纠错独立实现及验收，可信人工收款及转移仍为后续批次。批量单独维护运行验收，自动续费开关继续独立；不能采用旧转移流程删除未付账单后直接改归属。
