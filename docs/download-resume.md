# Resumable stored downloads

Local download-center files and customer files support `HEAD`, single and multipart `Range: bytes=...`, and `If-Range` on their existing file URLs. Service-scoped download URLs use the same download-center handler. A successful partial response is `206` with `Content-Range`; an unsatisfiable range is `416`. More than 16 ranges or an 8 KiB range header is rejected with `416` to bound multipart work. A stale `If-Range` returns the full current file.

The quoted SHA-256 content hash is the strong `ETag`. File replacement changes the tag. Every request passes the existing session or API-key, visibility, ownership, and product or sales-scope checks before file headers or bytes are sent. File responses retain `Cache-Control: private, no-store`, attachment disposition, and `nosniff`.

Authorized local `GET` responses with status 200 or 206 advance download counters; HEAD, 304, 412 and range errors do not. Customer file transfers retain their audit event in the same transaction. Response status is resolved before commit, with no headers or bytes sent on rollback. Remote URL downloads still return their existing JSON response and do not support byte ranges.

Browser consumers share the Blob-saving helper in `web/src/lib/download.ts`. Reports, contracts, ticket attachments, stored downloads and monitoring exports keep their own requests, permissions, errors and filenames. The helper removes temporary anchor elements and releases object URLs after a delay, including failed clicks. Stored downloads prefer a valid UTF-8 `filename*` response parameter and fall back safely when it is malformed. Remote URL responses keep their separate HTTP(S) navigation path; they are not fetched or converted to Blobs by the helper. `node --test scripts/download.test.mjs` exercises these boundaries with DOM/fetch fixtures, not a real browser.
