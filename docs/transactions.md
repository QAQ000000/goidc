# 订单与账单详情

原生交易页面初版于2026-10-06部署于schema055；后续schema060/061接入原生支付与查单，schema062增加循环续费权益快照，schema063保存[购买资料](product-purchase-fields.md)，schema064扩展[固定与限次续费](limited-renewal-benefits.md)。订单/服务读取完整资料快照，订单账单仅返回购买时允许账单展示的字段。旧 PHP 与旧数据仅作业务参考。

## 页面与接口

| 页面 | API | 访问范围 |
| --- | --- | --- |
| `/console/orders` | `GET /api/v1/orders/page` | 当前账户订单 |
| `/console/orders/{id}` | `GET /api/v1/orders/{id}` | 当前账户订单 |
| `/console/invoices` | `GET /api/v1/invoices/page` | 当前账户账单 |
| `/console/invoices/{id}` | `GET /api/v1/invoices/{id}` | 当前账户账单 |
| `/admin/invoices` | `GET /api/v1/admin/invoices/page` | `invoices.view` 及客户销售范围 |
| `/admin/invoices/{id}` | `GET /api/v1/admin/invoices/{id}` | `invoices.view` 及客户销售范围 |

原有订单、账单数组列表接口保留。新 `/page` 接口在 `data` 下返回 `{items,total,limit,offset}`；空的末尾页也返回真实总数。计数和项目使用同一只读 Repeatable Read 快照。API 默认 25 条，`limit` 有效范围 1–100，负 `offset` 归零；页面每页 20 条，按 ID 倒序。

订单状态支持 `pending/paid/active/cancelled/refunded`；账单状态支持 `unpaid/paid/cancelled/refunded`。`q` 去除两侧空白，最长 120 字节，非法状态或超长搜索返回 400。订单搜索订单号、历史产品名称，管理员额外搜索客户名称/邮箱；账单搜索账单号、关联订单号、账单项目描述和历史产品名称，管理员额外搜索客户名称/邮箱。

## 交易快照与权限

客户订单详情返回订单金额、优惠码/优惠金额快照、同一客户的关联账单、订单项目及服务。项目使用下单时的产品名称、账期、周期价、初装费、数量、配置和数量快照，修改当前商品或选项不改写历史订单。

客户订单列表和详情均不返回管理员备注、上游资源凭据、请求哈希或旧来源归档。未登录返回 401；访问其他账户详情返回 404。管理员订单备注继续由既有后台接口提供。

账单详情返回保存的 `invoice_items`、同一客户关联订单的 `order_items`、支付意图与余额付款/退款流水。原生购买账单没有独立账单项目时，前端展示订单项目快照，不创建虚构历史；续费和升级账单展示已有账单项目。服务链接只关联同一账单客户的服务。

订单项目保存购买时的续费比例/固定金额、次数上限和代码；续费账单项目额外保存周期原价 `renewal_base_cents`、优惠 `renewal_discount_cents`、权益与该次序号，实付等于原价减优惠。成功付款后消耗一次，退款只返实付且不恢复优惠次数。详情汇总展示实际优惠，不从当前优惠码重算历史。没有购买权益或次数用完的服务保持原价，详见 [循环续费优惠](recurring-promotions.md)。

支付意图和余额流水各最多返回最近 50 条。不返回支付渠道原始结果、幂等键或上游凭据。schema060 新增易支付协议适配、独立渠道流水和客户本人付款链接；后台详情隐藏付款链接。主动和 worker 查单可补结算并保存查询状态/时间，后台主动操作要求独立 `payments.reconcile` 权限和客户范围。运行框架按提供方能力支持可信关单及未知结果核验；Epay 不声明关单能力，不能以查到未付款或本地过期替代关闭。真实商户/原路退款到账、正式关单能力和完整历史分页须按[在线支付](payments.md)及[支付开发契约](architecture/payment-module-development.md)单列验收。

管理员账单详情使用 Read Committed，取得客户销售范围共享事务锁后重新检查当前归属，并锁定账单头供本次读取。销售转交持有排他锁；等待转交的读取在转交提交后重新校验范围，失去授权返回 404。管理员账单、订单及服务链接分别检查读取权限，仅有 `invoices.view` 的账户不展示退款和无权限资源链接。

## 支付与流程入口

客户余额付款继续使用 `POST /api/v1/invoices/{id}/pay`；模拟支付使用 `/payments` 的 `provider=mock`，页面明确标注模拟支付。配置真实商户后可使用原生易支付跳转；部署实例尚未配置真实商户。已存在模拟待处理意图时禁止再次创建模拟支付单，余额支付仍可用；真实待处理意图按下文限制。数据库账单状态和锁防止重复结算，余额付款后的成功渠道回调拒绝再次付款。

`payment_pending` 表示未付款账单存在 `pending/expired` 意图，或存在未决关单后到账异常；`real_payment_pending` 还排除模拟意图，并包含未决关单操作，页面据此禁用余额支付。真实在线意图阻止换渠道、余额支付和取消操作，详情可继续原付款或查单。意图可被 worker 标记为 `expired`，仍保留资金保护；Epay 没有关单能力，不能本地过期后直接重新开单。只有支持关单的提供方按可信关闭/独立核验流程确认终结并解除相关未决状态，才能按原付款规则重新开单。详情在未付款待处理时每 3 秒刷新，付款后停止。支付和退款按钮使用稳定幂等键重试。

取消待付款订单和管理员退款均有确认弹窗，操作后重新读取真实状态。管理员退款还需要 `invoices.refund`，继续遵循现有交付/复核约束。

客户退款、停用需求使用工单交给管理员核实；管理员在原账单退款，服务动作在服务详情单独处理。该流程不新增客户专用退款/停用申请入口或状态机，工单不直接触发财务和资源变更。原渠道资金及不支持的复杂退款仍按[人工操作手册](payment-operations-runbook.md#客户请求与管理员处理)处理，不能因收到工单就放宽退款边界。下节保留既有取消/续费安全规则与历史记录，不将其解释为新增供应商客户申请能力。

购物车结算成功直接进入返回的订单详情；订单详情可进入账单和服务；服务续费生成账单后直接链接该账单详情；未付款配置/商品升级账单也直接链接详情。

## 管理员代下单与回执

`POST /api/v1/admin/orders/quote` 报价后，`POST /api/v1/admin/orders` 使用原请求、`quote_hash` 和 8–128 字节的稳定幂等键提交。首次成功返回 201；相同管理员、相同键和相同规范化请求返回原结果及 `replayed=true`，状态为 200。更换客户、备注或其他请求字段后复用该键返回 `idempotency_conflict`。不同管理员、不同业务 scope 的同名键互不覆盖。

代下单统一使用 `ReplayOperation` / `SaveOperation`，scope 固定为 `admin:order.create`。事务先锁定并校验当前管理员的 `orders.manage`、客户销售范围及客户启用状态，再读取回执。撤权、客户转交或客户停用不能通过历史回执绕过；重放保持原报价结果，不重新扣库存、使用优惠码、创建订单/服务/账单或追加邮件、通知和审计。首次创建的这些副作用与回执同事务提交；审计失败整笔回滚，同键可以安全重试。付款方式仅是后续付款偏好，代下单不调用支付网关扣款或开通供应商资源。

迁移 `179_admin_order_mutation_receipts.sql` 将旧 `admin_order_creation_receipts` 归入统一表，原样保留请求 hash、JSON 结果、创建时间及 actor/customer/order 关联。统一表新增可空 `customer_id/order_id` 外键：只有该 scope 必须填写并与结果中的订单 ID 一致，其他 scope 必须为空。业务保存时通过 `OperationReferences` 传入这两项，保留旧记录对客户与订单的物理删除保护。

升级前停止旧 API、worker 和其他 writer，再执行迁移并启用配套二进制。迁移先排他锁旧表；历史客户与订单归属或保存结果不一致时返回 `admin_order_receipt_requires_reconciliation`；统一 scope 冲突、无效 hash/结果等也会拒绝升级，不覆盖任一回执。整次迁移失败会保留旧表、原记录及 schema178；先核实歧义数据再重试。成功后旧表移除，不支持混跑旧 writer 或在新 schema 直接降级旧二进制；回退需要恢复配套升级前备份。

`node scripts/test-admin-orders.mjs --integration` 在独立回环 PG18 测试库逐项要求 run/pass 且零 skip，覆盖原键历史重放、actor/scope 隔离、八请求并发、异参冲突、撤权竞态、客户范围、库存/优惠/邮件/通知单次、审计回滚及真实 schema178 起点升级。合成旧 writer 夹具只证明代码和迁移兼容；浏览器、真实邮件/供应商、远端 CI 和生产升级须独立验收。

## 服务取消与续费互斥

取消申请为 `pending` 时，客户仍可创建续费账单并付款；续费不自动批准或撤回取消申请。管理员随后批准按账期取消时，终止任务使用服务当时最新的 `next_due_at`。`approved` 后禁止新建续费账单，也禁止已有未付续费账单通过余额、信用或在线意图继续付款，返回 `service_cancellation_approved`。相同幂等请求仍可读取已有结果，不产生新付款或新权益。

批准前必须核清所有关联续费账单的在线支付：非 `mock` 意图处于 `pending/expired`，或存在未决关单操作、关单后到账异常时，返回 `invoice_payment_pending`，不改申请、不建终止任务。不能用拒收既有真实回执或删除支付意图来实现取消互斥；可信关闭后的迟到成功仍进入原到账异常记录及核验流程，见[支付契约](payments.md)。

新建续费、批准/撤回取消都以服务行串行；审批先锁服务，再锁申请。付款和在线意图保留既有账单锁顺序，再按服务 ID 顺序 `FOR UPDATE NOWAIT` 取得关联服务，冲突返回 `service_action_pending`，避免持有资金锁反向等待服务。数据库迁移 169 同时保护续费账单付清、新支付意图和取消批准；不能只部署 API 判断而遗漏数据库与 worker 防线。

终止执行前再次核验申请归属/批准状态、未决在线资金和当前权益。按账期取消若发现当前到期日比原任务时间晚且尚未到期，原任务改排到当前到期日；立即取消若发现批准后已付续费则停止执行、要求核验。未批准的任务取消，未决资金阻止终止；已派发的外部动作保留未知结果并进入核验，不能自动重发。人工交付模式的终止任务等待确认时保留原 `active/suspended` 等服务状态，确认成功才反映终止，不提前写成 `provisioning`；人工开通仍使用 `provisioning`。

### 历史冲突与发布边界

`169_cancellation_renewal_admission.sql` 检查旧版已批准取消与批准后已付续费、未决在线支付的冲突。只有原终止任务仍为 `pending` 且 `external_started_at IS NULL`，并且同服务没有另一条待审或已批准申请时，才自动取消原任务、将申请重开为 `pending`；审计保留原申请与原任务快照。订单、账单、账本、支付意图/回执和续费权益事实保持原样。资金核清后重新批准递增 `approval_generation`，以 `service-cancellation-{requestID}-{generation}` 创建新任务，不覆盖旧任务或重用旧派发身份。

缺少关联任务、任务已运行/等待人工/等待核验/已派发，或同服务另有待审/已批准申请等歧义历史，会以 `cancellation_renewal_requires_reconciliation` 拒绝整次升级，错误明示服务、申请、任务 ID。必须先人工核实资源和收款，再重试；不得为通过迁移删除回执或改写资金事实。

迁移 169、API 与 worker 必须成套发布。升级前停止旧 API、旧 worker 及其他可能写入取消/续费/账单的旧进程，再迁移、检查 checksum/schema 并启用配套候选；不能让旧 writer 与新规则混跑，也不能在新 schema 上直接回退旧二进制。回退须按[切换手册](cutover-runbook.md)使用明确匹配的代码、数据库和恢复点重新验收。当前迁移目录有 170 个 SQL 文件、最大编号 169，身份仍以完整文件名及 checksum 为准。
