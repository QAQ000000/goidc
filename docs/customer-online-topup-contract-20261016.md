# 客户自助在线充值实施契约（2026-10-16）

状态：下列设计已在独立分支实现并集成；隔离运行与四尺寸浏览器结果见[集成验收](customer-online-topup-acceptance-20261016.md)。最终隔离PG18全量回归已通过；真实商户付款与待补账解决入口尚未验收或实现。本文保留实施前的设计边界，最终接口、数据事实和限制以验收记录及源码为准。

## 现有基础

`internal/store/finance.go` 的 `TopUp` 是管理员直接加余额，不能由支付回调调用它另开事务。现有财务设置已有充值开关、单笔最小/最大、余额上限和需已有 paid/active 订单规则；账本有用户/类型/幂等键唯一保护、余额非负约束。

实施前账单只有 automatic/manual 两类；迁移144及结算分支现已新增专用topup账单和唯一充值事实，禁止伪装人工服务项目。现有真实支付意图、商户快照、异步通知验签、查单和重复成功保护可复用；指定商户可信查单/关单限制仍存在。

## 完整链路

1. 客户会话读取充值选项：开关、范围、是否满足订单条件、可用网关和余额限制。创建接口只绑定当前客户，金额使用整数分，不接受任意 user_id。
2. 创建独立 `balance_topups` 与 `invoice_kind=topup`，保存金额、设置版本/接纳资格快照和请求摘要。用户级幂等键同键同参返回同单、异参 409。
3. 初次创建真实支付意图前锁定资格与余额额度，计算同客户已接纳但未终结支付的预留额度，避免并发多单分别通过余额上限。禁止余额或信用支付充值；禁用后不再接纳新付款，但不能抹去已接纳款项。
4. 网关成功通知在现有事务中结算：保存原成功收款、充值入账唯一事实、余额更新、账本、账单/充值状态、审计及通知原子提交。唯一保护覆盖充值单及原支付，不只依赖通知 event_id；不同事件 ID 重复成功不能再加余额。
5. 充值不创建订单或服务、不排开通、不发佣金。余额流水标明网关充值与原支付，客户可从充值结果追溯原账单和支付状态。
6. 未付款取消/过期沿用真实付款限制：本地过期不代表原支付不可收款，不能据此释放仍可能到账的接纳额度。未知结果可核对，不能标成失败后盲目重建支付。

## 资金边界

回调必须按接纳时快照处理设置关闭、范围变化、订单失效等情况；真实已收款不能因最新开关拒绝并丢失收入事实。充值期间后台加款和余额消费也会影响限额，须统一客户资金锁及额度规则。若意外无法入账，必须原子记录真实收入与明确待处理负债，不得返回假成功或把商户成功当未付款。

现网回调先锁原支付再锁账单，余额消费先锁客户。接入充值不能持 payment/invoice 锁后反向等待客户锁；修改公共资金锁序前列出全部回调、对账、余额/信用购买、管理员加款及退款路径，再做并发验证。

第一增量明确禁止充值退款。若后续开放，需要申请时冻结等额可用余额、独立复核后原子扣余额并追加外部退款事实，驳回释放冻结；不能复用仅修改人工账单状态的外部退款路径。资金已经外部退回而余额被花掉的情况不能靠状态更改修补。

## 财务口径

充值网关收款是现金收入，充值余额流水是内部账户变动；随后使用余额购买是消费结算，不能再当同一笔外部现金收入。交易现金汇总现按成功 payment 事实计算，可复用；现年度/销售报表按 paid 非信用账单统计，包含余额购买，接入充值前必须一起明确并修订口径。应独立展示现金收退款、消费收入、余额负债，保留各来源追溯，禁止简单追加充值账单导致双计。

## 验收

- 强制隔离 PG18 迁移与 HTTP：归属/会话、金额范围、开关和订单条件、同键重放/异参、不同键并发额度、余额/信用买充值拒绝。
- 真正事务与 race：重复/不同事件成功通知、设置变化后的迟到款、充值与余额消费/后台加款竞争、回调和对账并发；入账失败无部分余额/事实更新，成功不重复入账、不产生服务或佣金。
- 财务断言：网关现金只计一次，余额/消费来源独立、充值负债可追溯，退款路径明确拒绝充值。
- 四尺寸浏览器：真实选项、创建/取消、支付跳转、结果/未知/失败/错误恢复、刷新和返回上下文；真实扫码、通知、查单单列第三方验收，不能把 mock 成功当真实付款。

已注册入口：`GET /api/v1/balance/topup-options`、`POST /api/v1/balance/topups`、`POST /api/v1/balance/topups/{invoice_id}/cancel`，支付沿用当前客户账单接口。验收记录明确列出已实现范围、并发与资金边界；原商户真实付款另列待验收，不以本地协议测试代替。
