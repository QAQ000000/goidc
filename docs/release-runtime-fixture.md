# Opt-in runtime database fixture

This helper is test code, not a runtime service. It prepares and inspects a private database fixture while the JavaScript controller runs the verified package's migrate/API/Web/worker. It does not compile binaries, migrate the protocol schema itself, launch workers, claim jobs or call providers. The separate opt-in contract test does use local Store migration/claim/process calls to verify the helper's own assertions; those checks are not same-package worker acceptance.

Start only from the fixed clean candidate source:

```sh
ZJMFGO_RELEASE_RUNTIME_FIXTURE=1 \
ZJMFGO_RELEASE_RUNTIME_FIXTURE_DIR=/absolute/new/exclusive-0700-directory \
ZJMFGO_TEST_DATABASE_URL='[private dedicated loopback PG18 URL]' \
go test -run '^TestReleaseRuntimeFixture$' -count=1 -timeout=15m ./internal/store
```

The URL must use `postgres`/`postgresql`, `127.0.0.1`, explicit port, a database ending `_test`, and only optional `sslmode=disable|prefer`. Query host/port/options/search_path overrides are refused before connecting. Parsed driver host/database/port are checked again. The server must be PostgreSQL 18, report the expected database and actual IPv4 loopback address. Every run creates exactly one unpredictable `release_runtime_` plus 24 lowercase hex schema. Configured child DSN includes only that schema's `search_path`, a unique runtime `application_name`, `sslmode=disable` and bounded connection timeout. The fixture control/base connections use separate application names.

The caller creates an empty ordinary directory, mode `0700`, with no symlink components. Fixture writes `config.json` mode `0600` containing `{version:'zjmfgo-runtime-config-v1',values:{DATABASE_URL,MFA_ENCRYPTION_KEY,PURCHASE_FIELD_ENCRYPTION_KEY,PROVISION_ENCRYPTION_KEY}}`. Keys are newly random and DSN exists only in that private file and process memory. Never print or copy the config into reports. An outer privileged controller may explicitly chown only this owned directory/config to its ordinary runtime UID; it must not change shared directories. All other responses are mode `0644` and contain only redacted metadata.

The file protocol is sequential and bounded to 12 minutes. Responses are published by exclusive temporary file plus rename. Commands are ordinary files, mode `0600`, at most 4096 bytes, named `command-N.json` starting at 1, JSON `{operation:'...'}`. Publish each command atomically and wait for matching `result-N.json` before the next. Invalid JSON or unknown operations are rejected without echoing input. Response `{ok:false,errorCode:'sanitized explanation'}` means the operation failed; it is not a pass. The caller must stop its own package processes before requesting cleanup.

1. Wait for `schema-ready.json`: `{ok:true,phase:'schema-ready',schema,database,pgVersion,applicationName}`. The schema is empty. The fixture has not run migrations.
2. Run package `migrate`; command `verify-migrations` checks exact embedded migration checksums and records the complete table/column/constraint/index/function/trigger plus seeded-row digest as `migrationSchemaSHA256`.
3. Run package `migrate` a second time; command `verify-migrations` requires identical structure, migration checksums and seeded data. Both checks must precede `prepare`.
4. Command `prepare` requires the empty migrated business tables, disables all external channels, templates, scheduler triggers and affiliate program in this schema, creates only synthetic unverified customer/product/approved order/item/suspended simulation service, and enqueues one legitimate `resume` through `EnqueueServiceAction`. No success fields are fabricated. Response includes `serviceID`, `jobID`, `initialServiceVersion`, `baselineSHA256` and `safeInputs:true`.
5. Start the package worker. Command `verify-first` returns `{ok:true,pending:true,state}` while pending/running. Successful completion requires `succeeded`, `active`, result mode `simulation`, action `resume`, exactly one attempt, service version increased by exactly one, and exactly one matching `service.simulation.completed` audit. Full baseline business rows, balances, payment/credit/ledger/notifications, settings and all service fields except intended status/version/update timestamp must stay unchanged. No unrelated job, enabled channel, supplier account, non-simulation/auto-renew/due service, invoice/payment/affiliate due work or notification outbox/event is permitted.
6. TERM and await worker exit, restart the same package worker, and allow at least one worker poll interval. Command `verify-restart` requires the full successful service/job/audit snapshot remain unchanged; summary fields alone cannot hide a duplicate or a changed result. The first successful snapshot cannot be replaced by repeated `verify-first` calls. An explicit successful `verify-restart` is required before `finish`.
7. Stop all owned package services and close the controller's DB bridge. Command `finish` rechecks completion/restart invariants, requires zero connections with this fixture's unique runtime application name, closes its own pool, drops only its validated owned schema and proves it absent. It removes `config.json` and writes `done.json` `{ok:true,phase:'cleaned',schemaRemoved:true}`. On failure use `abort`, which skips completion assertions but still requires owned runtime connections gone before deleting its schema. It never terminates database connections or deletes unrelated schemas.

The business baseline covers every ordinary schema table except the intended service/job/audit execution, `external_refund_delivery_history` and `scheduler_runs`. Migration 154's service guard legitimately appends exactly one `service_changed` history row on resume; the helper requires that row to match this service/order, preserves the entire earlier history, and freezes all history bytes after first completion. The worker records scheduler polls even for disabled tasks; those records may change only with zero affected rows. All service fields outside status/version/update timestamp remain bound, and no additional service is allowed.

The fixture does not prove the runtime's network namespace, bundled binary identity, actual TERM/restart, route/chunk behavior or write boundaries; the controller must produce that evidence. Local database assertion tests must not be reported as real worker-process acceptance. The new migration/schema is empty-database acceptance only and does not prove upgrade of a business snapshot.

Focused verification: `TestReleaseRuntimeFixtureContract*` covers unsafe DSNs, foreign schema names, private files, exclusive responses and command mode. Set `ZJMFGO_RELEASE_RUNTIME_FIXTURE_CONTRACT=1` with a dedicated PG18 test URL to include `TestReleaseRuntimeFixtureDatabaseContracts` and `TestReleaseRuntimeFixtureProtocolContract`: real safe fixture preparation/consumption checks, tamper rejection, private-config/log boundaries and abort schema cleanup. These tests never use an external provider or an application database.
